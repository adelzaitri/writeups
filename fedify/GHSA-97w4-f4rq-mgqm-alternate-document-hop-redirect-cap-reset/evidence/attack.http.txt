================================================================================
WHERE THE CHECK SHOULD HAVE BEEN
================================================================================

packages/vocab-runtime/src/docloader.ts. The loader carries both bounds as default parameters:

  async function load(
    url: string,
    options?: DocumentLoaderOptions,
    redirected = 0,
    visited = new Set<string>(),
  ): Promise<RemoteDocument> {

and the 3xx path correctly threads them through:

            return await load(redirectUrl, options, redirected + 1, visited);

That same `load` is handed to `getRemoteDocument()` as its `fetch` parameter:

          const result = await getRemoteDocument(currentUrl, response, load);

and `getRemoteDocument()` calls it with ONE argument on both alternate-document hops:

  :192  return await fetch(altUri.href);
  :244  return await fetch(new URL(attribs.href, docUrl).href);

Because `redirected` and `visited` are **default parameters**, a one-argument call resets the
counter to 0 and the visited set to empty — and `options` becomes `undefined`, taking
`options.signal` with it. The fix is to thread the state the 3xx path already threads.

The same shape is present in the authenticated loader, which passes its own `load` the same
way: packages/fedify/src/utils/docloader.ts:87
`return getRemoteDocument(url, response, load);`

================================================================================
REACHABILITY — unauthenticated, in a default integration
================================================================================

`getDocumentLoader()` is the default document loader. HTTP-Signature verification fetches the
remote `keyId` during inbound request processing — packages/fedify/src/sig/key.ts:825:

    try {
      const remoteDocument =
        await (options.documentLoader ?? getDocumentLoader())(
          keyId,
        );

`keyId` comes out of the inbound `Signature` / `Signature-Input` header, so the trigger is an
unauthenticated `POST` to any inbox or shared inbox. That is the parent advisory's own stated
path, quoted from GHSA-gm9m-gwc4-hwgp: *"Fedify verifies ActivityPub HTTP signatures by
fetching the remote keyId during request processing. The relevant flow is
handleInboxInternal() -> verifyRequest() -> fetchKeyInternal() -> document loader."*

Nothing beyond an ordinary `createFederation()` integration is required, and
`allowPrivateAddress` stays at its default `false` — the destination is the attacker's own
public host, so the SSRF guard is not in the path.

SCOPE AND CONFIGURATION, STATED PLAINLY
================================================================================

- **This instance only.** Every server binds to 127.0.0.1. No fediverse instance, no hosted
  service, and no third party was ever contacted. The packages came from the public npm
  registry; the integrity hashes are in versions.txt.
- **`allowPrivateAddress: true`** is set in every row so the lab can stay on loopback. It
  gates `validatePublicUrl` only, and the control run proves it does not disable the redirect
  bound. See control.http.txt.
- **`maxRedirection: 2`** is set explicitly so the bound is small enough to observe. The
  default is larger; the finding is that on this hop NO value has any effect, which the
  60-request and 2800-request runs show.
- **The stop-after is ours.** The lab terminates its own loop. Nothing here ran unbounded
  against anything, including this host.
